## 3. 실행 환경 트러블슈팅 (재현 시 그대로 따라할 것)

1. **권한**: 초기 "don't ask" 모드에서 바이너리 실행·git·sysctl 전부 자동 거부 → 사용자가 automode 전환 후 해결.
2. **rpath 깨짐**: 리포가 `/Volumes/X31/llama.cpp` → `/Volumes/X31/optillama/llama.cpp`로 이동된 이력 때문에
   옛 빌드 바이너리의 `@rpath`가 절대경로로 옛 위치를 가리킴.
   증상: `dyld: Library not loaded: @rpath/libllama-cli-impl.dylib`.
   임시 해결: `DYLD_LIBRARY_PATH=<bindir>` (common.sh에 반영). 근본 해결: 새 빌드.
3. **cmake 부재**: 옛 빌드는 `/opt/homebrew/bin/cmake`를 기록하고 있으나 이 머신에 cmake 없음
   → `brew install cmake`.
4. **옛 빌드 디렉토리 재구성 불가**: `CMakeCache.txt`에 옛 소스 경로 고정
   ("directory ... is different than ... where CMakeCache.txt was created")
   → `build-m1/` 신규 구성으로 우회. **옛 build-m1max-* 디렉토리는 앞으로 사용 금지.**
5. 새 빌드 명령 (전체):
   ```bash
   /opt/homebrew/bin/cmake -S /Volumes/X31/optillama/llama.cpp -B /Volumes/X31/optillama/llama.cpp/build-m1 \
     -DCMAKE_BUILD_TYPE=Release -DGGML_METAL=ON -DGGML_METAL_EMBED_LIBRARY=ON -DGGML_ACCELERATE=ON
   /opt/homebrew/bin/cmake --build /Volumes/X31/optillama/llama.cpp/build-m1 \
     --target llama-cli llama-bench llama-perplexity llama-quantize -j 8
   ```
   (빌드 중 "UI: download dist.tar.gz failed" 경고는 무해 — TUI 웹에셋 다운로드 실패일 뿐)

## 5. 근본 원인 분석 (소스 코드 수준 — 재발견에 시간 쓰지 말 것)

### 5.1 Metal 오프로드 OOM의 구조적 원인 (smoke1/2/3 교차 검증)
- `src/llama-model.cpp` 버퍼 생성부(패치 전 ~1557행): `use_mmap && buffer_from_host_ptr && is_default_buft`이면
  `ml.get_mapping_range(&first,&last,...,ctx)`로 **"해당 buft 소속 텐서를 전부 포함하는 연속 파일 구간"**을 계산해
  `ggml_backend_dev_buffer_from_host_ptr()` 한 방으로 감쌈.
- `-ncmoe`를 써도 attention 텐서는 blk.0~blk.48 전역에 expert와 교차 배치 → Metal buft의 [first,last) ≈ **파일 전체 ~37GB**.
- Metal/IOGPU는 커맨드버퍼가 참조하는 MTLBuffer를 제출 시점에 **통째로 wire** (GPU는 페이지 폴트 불가).
  37GB wire > 16GB RAM (recommendedMaxWorkingSetSize 12.7GB) → `kIOGPUCommandBufferCallbackErrorOutOfMemory`.
- residency set(`GGML_METAL_NO_RESIDENCY`)은 별개 메커니즘이라 무관 — smoke3로 입증.
- 결론: **Metal에 file-backed 별칭 버퍼를 주는 한 어떤 런타임 플래그로도 회피 불가.** 복사 버퍼(패치 2)가 유일한 하이브리드 경로.

### 5.2 전체 파일 WILLNEED readahead의 자해 (smoke1 실측 139GB)
- `src/llama-model.cpp:1518` → `init_mappings(prefetch=true)` 하드코딩 → `src/llama-mmap.cpp:462-464`
  `posix_madvise(addr, min(size,prefetch), POSIX_MADV_WILLNEED)` — 파일 전체.
- RAM보다 큰 파일이면: readahead가 캐시를 채우고→자기가 밀어내고→다시 읽고 순환. 실측 139GB(3.7배) 페이지인.
- 로드 ~1분 낭비 + 유효 캐시 파괴 + Metal wire용 여유 메모리 고갈에도 기여.

### 5.3 MTP 투기 디코딩이 I/O-bound에서 역효과인 이유 (smoke7: TG 0.9→0.5)
- MTP 검증은 드래프트 k개를 한 배치로 처리. 절약되는 것은 "여러 토큰이 같은 expert를 쓸 때의 중복 읽기"인데,
  **연속 토큰 간 중복은 어차피 페이지 캐시가 흡수**하고 있었음.
- 반면 (a) 토큰별 라우팅이 거의 서로소라 배치의 expert 합집합 ≈ k×8 (I/O 절감 없음),
  (b) 기각된 드래프트의 expert 읽기가 순수 추가 비용, (c) 드래프트 생성 자체의 비용.
- MTP는 연산-bound 환경 전용. 이 하드웨어에서는 재시도 금지.

### 5.4 prefill op-offload 역효과 (smoke6: PP 1.4→0.8)
- `ggml_backend_sched`는 host 가중치 op를 batch≥32(GGML_OP_OFFLOAD_MIN_BATCH)에서 GPU로 보내며
  사용 expert 가중치를 GPU 버퍼로 복사. 콜드 상태에서는 이 복사 자체가 디스크 읽기 → GPU 전송의 이중 비용.
  expert가 RAM에 상주 가능한 시스템에서만 유효한 최적화.

### 5.5 새 llama-cli(TUI)의 EOF 스핀 버그 (사고 1회, 로그 797MB)
- decode 에러 후 대화 모드로 폴백 → stdin이 EOF/닫힘이면 `console::readline`이 fflush/write를 무한 반복 (CPU 100%).
- 회피 표준: `-no-cnv -st` + `</dev/null` + 워치독(kill -TERM 타이머) + 로그 크기 감시. 하니스에 반영됨.

#include <sys/mman.h>

// mul_mat_id 정의부 앞:
// with mmap-backed expert weights larger than RAM, cold expert slices fault
// page-by-page inside the matvec; advising the kernel up front overlaps the
// read-ahead with compute (GGML_MOE_PREFETCH=1 to enable)
static int ggml_moe_prefetch_enabled(void) {
    static int enabled = -1;
    if (enabled == -1) {
        const char * e = getenv("GGML_MOE_PREFETCH");
        enabled = e != NULL && e[0] != '0';
    }
    return enabled;
}

#if !defined(_WIN32)
static void ggml_moe_prefetch_slice(const void * base, size_t len) {
    const size_t page = 16384;
    uintptr_t a0 = (uintptr_t) base & ~(page - 1);
    uintptr_t a1 = ((uintptr_t) base + len + page - 1) & ~(page - 1);
    posix_madvise((void *) a0, a1 - a0, POSIX_MADV_WILLNEED);
}
#endif

// ggml_compute_forward_mul_mat_id 내부, ith==0의 라우팅 그룹핑 루프 종료 직후:
#if !defined(_WIN32)
        if (ggml_moe_prefetch_enabled()) {
            for (int cur_a = 0; cur_a < n_as; ++cur_a) {
                if (matrix_row_counts[cur_a] > 0) {
                    ggml_moe_prefetch_slice((const char *) src0->data + cur_a*nb02, nb02);

        }
#endif

## 9. 병목의 정량 모델

### 9.1 토큰당 expert 바이트
- expert 풀 33.36GiB ÷ (49층 × 256 expert) ≈ **2.66MiB/expert/층** (gate+up+down 합)
- e8: 49 × 8 × 2.66MiB ≈ **1.04GiB/토큰** · e6: 0.78GiB · e4: 0.52GiB

### 9.2 캐시 적중률
- 가용 페이지 캐시 ≈ 16GB − (상주 4.2GiB는 ngl0에서는 mmap 공유라 캐시 겸용) − OS/앱 ≈ **~10GiB**
- 균등 접근 가정 적중률 ≈ 10/33.4 ≈ **30%** (실제는 라우팅 편향으로 약간 상회)
- e4는 접촉 풀 축소 + 재사용 빈도 상승으로 적중률 추가 개선 → 초선형 TG의 근원

### 9.3 상한 계산 vs 실측
| 구성 | 콜드 바이트/토큰 | 실효 읽기 (madvise readahead, 내장) | 예측 TG | 실측 TG |
|---|---:|---:|---:|---:|
| e8 | ~0.7GiB | ~2.5GB/s | ~2.8 t/s | 1.8~2.5 ✓ |
| e4 | ~0.3GiB | ~2.5GB/s | ~5-6 t/s | 3.8~4.3 ✓ (연산 몫 추가) |
- 모델과 실측이 정합 → **남은 개선축은 (a) expert 수, (b) expert 풀 바이트(더 낮은 양자화), (c) 가용 RAM, (d) 프리페치 심도**뿐.
- 연산 가속(GPU/dequant/투기)은 이 병목에 안 걸림 — 전부 실측 기각 완료.

### 9.4 이 모델이 말해주는 것
- 무손실 5 t/s를 만들려면 콜드 바이트/토큰을 ~0.35GiB 이하로: (i) expert 풀을 ~24GiB로(IQ1_M급, 품질비용) 낮춰 적중률 ~42%를 얻거나, (ii) RAM 증설(불가) 또는 (iii) 라우팅 지역성 활용(연구 영역).
- 즉 **16GB에서 e8 무손실 5 t/s는 물리적으로 빡빡**하고, 정직한 선택지는 e6(+~5% PPL, ~2.5t/s)과 e4(+~20%, ~4t/s) 사이에 있다.

## 13. 운영 함정·사고 기록 (전부 실제로 겪은 것)

1. **로그 797MB 사고**: smoke1에서 CLI가 에러 후 EOF 스핀하며 스피너를 로그에 무한 기록. → `-st` + `</dev/null` + 워치독 + 로그 크기 확인 습관.
2. **중복 실행 사고**: R3 1차에서 llama-cli 2개가 동시 구동(19:08/19:11 스탬프 로그 2개)되어 측정 오염 → pkill 후 단독 재실행으로 해결. **벤치 전 `ps aux | grep llama-cli` 확인 필수.**
3. **glob tail 함정**: `tail -c N smoke.*.log`는 여러 파일에 걸리면 출력이 섞임 — 최신 파일을 `ls -t | head -1`로 특정 후 읽을 것.
4. **로그가 \r 스피너로 오염됨**: `LC_ALL=C sed 's/[^[:print:]]/\n/g'`로 정제 후 grep.
5. **build-m1max-* 재사용 금지** (3절), **cmake는 /opt/homebrew/bin/cmake**.
6. 스크립트 경로: common.sh의 ROOT/MODEL은 이 세션에서 optillama 경로로 수정 완료. smoke.sh에 `MODEL_OVERRIDE`/`T`/`EXTRA`/`NGL`/`OPOFF` 오버라이드 추가 완료.
7. gguf-py는 이 머신 python3에 numpy가 없어 못 씀 (필요 시 `pip3 install numpy` 또는 llama-cli 로드 로그 활용).

## 14. 한계점과 미해결 문제

1. **무손실 5 t/s 미달** — 9절 모델이 보여주듯 16GB RAM의 물리 한계. 정직한 상한: e8에서 ~2.5-3 t/s.
2. **PP가 8k 프롬프트에 비실용적** (3~5 t/s → 27~45분). **미검증 최대 지렛대: `-ub 2048/4096`** —
   prefill은 ubatch마다 expert 풀을 한 번씩 순회하므로 ubatch 4096이면 순회 횟수 16→2로 감소. 이론상 PP 수 배.
3. **8k 컨텍스트 장시간 안정성 미검증** — 짧은 생성만 확인. KV q8_0 vs f16 비교도 미실시 (GQA-2라 절대량은 작음).
4. PPL 8청크 축약 — 최종 채택 전 청크 확대 재측정 권장. e4/e6의 실사용 품질(한국어/코딩/추론) 스팟체크도 필요.
5. ~~IQ2_M e6/e4 PPL~~ 측정 완료 (e6 +4.8%, e4 +24.0% — 8절).
6. madvise 프리페치는 같은-op 한정 — 레이어 파이프라이닝 프리페치는 미구현 (15절 #6).
7. 콜드/웜 구분 측정 미체계화 — 현 수치는 혼합 상태. `sudo purge`로 콜드 통제 측정 가능(sudo 필요).
8. llama-server 미빌드 — 실서비스 형태 검증 없음.
9. 내장 SSD에 expQ2K 41GB가 아직 남아있음 (삭제 예정, 파일: `/Users/angigyeom/optillama-models/Qwen3.5-122B-A10B-expQ2K.gguf`).
