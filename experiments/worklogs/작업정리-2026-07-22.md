## 1. 한 줄 결론

**20 tok/s는 "expert 풀의 RAM 상주화" 없이는 물리적으로 불가능하고, 상주화하면 도달 가능 범위다.**
- 20 tok/s = 토큰당 50ms → 콜드 읽기 예산 ~100MB/토큰. 실측 콜드 바이트는 0.7~1.0GiB/토큰 → **8~12배 감소 필요.**
  프리페치/파이프라이닝 계열(Tier-2)은 전부 합쳐도 ~2×가 상한 → 구조적 수단(프루닝+저비트+expert 수)이 필수.
- 상주 달성 시 상한은 RAM 대역폭이 결정: IQ2_M e8 기준 ~3.4GB/토큰 ÷ 40-60GB/s ≈ **12~17 t/s**,
  expert 서브2비트화 또는 e6 결합 시 **~20-25 t/s**. 즉 목표가 상주 시나리오의 상단에 걸려 있다.

- Metal 전체 오프로드, prefill op-offload, t8, 전체 파일 WILLNEED: 21일 실측 기각 그대로.

## 4. 20 t/s 로드맵 (누적 스택, 전부 측정 게이트 뒤에 있음)

| 단계 | 수단 | 예상 TG | 품질 비용 | 필요 작업 |
|---|---|---:|---|---|
| 0 | 현재 (IQ2_M, 프리페치, t4) | 1.8~4.3 | 기준 | — |
| 1 | +룩어헤드 프리페치 (AHEAD=2~6 스윕) | 3~6 | 없음 | 벤치 30분 |
| 2 | +e6 (`expert_used_count=6`, PPL +4.8% 실측 완료) | 4~8 | 소 (실측됨) | 사용자 선택 |
| 3 | +핫 expert 핀 (통계 기반 mlock ~5-6GiB) | +10~20% | 없음 | 프로파일링 런 1회 필요 |
| 4a | REAP-97B(-22%) 드롭인 + 위 전부 | 6~10 | 미검증 (PPL 필수) | 다운로드 완료 후 벤치+PPL |
| 4b | 자체 프루닝 256→160~128 (통계 랭킹, prune_experts.py) | 8~14 | **중 — 반드시 PPL+실사용 평가, 사용자 승인** | 프로파일링 런 → 프루닝 → 평가 |
| 5 | 프루닝 + expert IQ1_M 재양자화(imatrix 필요) → 풀 ~11GiB **RAM 상주** | **12~22** | **대 — 단계별 평가 필수** | imatrix 런 + requant + 평가 |

- 주의: 4b/5의 프루닝 랭킹은 빈도 기반(우리 통계)이라 REAP saliency보다 열등할 수 있음 — REAP 논문의 게이트가중 노름 방식이 상위호환이지만 HF 원본 체크포인트+캘리브레이션 런이 필요. 1차는 빈도 기반으로 측정하고 결과로 판단.
- 대안 경로: 4a REAP-97B를 추가 프루닝(200→128)하는 조합이 자체 프루닝보다 품질 우위일 가능성 (REAP saliency로 이미 최악 56개 제거됨).

```bash
  --src <원본.gguf> --dst <출력.gguf> --keep 128 --stats moe_stats.csv

```

## 9. 자체 expert 캐시 매니저 구현 (2026-07-22 오후, 지시: "전부 자체 구현 허용, X31 사용, 20 t/s")

- 새 패치: **`GGML_MOE_CACHE_MB=<예산>`** (ggml-cpu.c, ~300줄) — OS 페이지캐시 의존을 버리고
  routed expert 슬라이스를 명시적 RAM 캐시로 관리. 업스트림 이슈 #20757이 요청만 하고 아무도 구현 안 한 구조.
  - **비동기 채움**: 전용 워커 스레드가 룩어헤드 예측(AHEAD 패치)과 실제 사용 expert를 mmap에서 복사.
    계산 경로는 절대 채움을 기다리지 않음 — 미스면 종전처럼 mmap로 읽고, 다음 토큰부터 히트.
  - **세그먼트 LRU**: 채움 직후는 probation, 실제 사용되면 protected로 승격 →
    prefill 스윕/오예측이 핫셋을 밀어내지 못함. 이번 토큰이 참조한 블록은 축출 금지(epoch 핀).
  - `GGML_MOE_CACHE_MLOCK=1`로 캐시 메모리 와이어링 옵션.
  - 주기적 히트율 리포트 (stderr, 16384 acquire마다).
- **정확성 검증 완료**: OLMoE-1B-7B IQ3_M (X31)에서 캐시 on/off 생성 텍스트 **비트 동일**, 히트율 89.9%.
  - 발견: Q4_K 등 k-quant는 ARM repack 경로(`ggml_cpu_extra_compute_forward`)로 우회되어 캐시를 안 탐.
    우리 타깃(IQ1/IQ2 i-quant)은 repack 미지원이라 항상 캐시 경로 사용.
- 다운로드 완료: unsloth **UD-IQ1_M 34.2GB** → `models/Qwen3.5-122B-A10B-GGUF-IQ1M/` (122B 전체 유지, expert ~1.75bpw)
- 테스트용 소형 MoE: `models/OLMoE-test/` (Q4_K_M 4.2GB + IQ3_M 3.1GB — 검증 후 삭제 가능)

**판정: 명시적 아레나 캐시는 16GB 통합메모리에서 순손실.** 아레나는 페이지캐시와 같은 RAM을
쪼개 쓰므로, 고정 4~5GB 아레나 < 적응형 ~10GB 페이지캐시. 정확성은 검증됐으므로(OLMoE 비트 동일)
